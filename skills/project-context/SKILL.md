# Project Context

## 核心定位

`CONTEXT.md` 是项目当前状态的精简快照，不是聊天记录、操作日志或历史档案。

本 skill 规定 AI 如何读取、核对、重建和校验上下文。

上下文的目标是让下一次会话快速理解项目并继续工作。只有会影响后续判断、执行或复现的问题才应保留。

## 触发时机

发生以下情况时执行一次完整同步：

- 新会话开始，先读取项目根目录的 `CONTEXT.md` 全文。
- 完成功能、修复、探查、验证或一个阶段。
- 发现、解决、替代或放弃一个问题或下一步事项。
- 用户明确修正事实、偏好、范围或完成状态。
- 做出会影响后续工作的决定。
- 收到 hook 的上下文维护提醒。
- 用户明确要求“更新上下文”或 `update context`。

没有改变项目事实的普通闲聊不需要改写文件。

## 完整同步协议

每次同步都按以下顺序执行，不能只追加本轮新内容：

1. 确定项目根目录，读取现有 `CONTEXT.md` 全文。不存在时，先说明情况，不凭空创建内容。
2. 枚举文件中的所有事实、任务、路径、版本、问题、决策、表格行和复选框。
3. 收集当前证据。优先使用用户本轮明确说明、当前项目文件、Git 状态、实际命令结果和可复现验证；时间敏感的外部事实才使用联网搜索。
4. 将每一条旧内容判定为保留、更新、合并、删除、转为历史或标记待确认。
5. 将本轮确认的新事实合并到正确区块，消除重复内容，处理互相冲突的内容。
6. 重新生成完整的 `CONTEXT.md`，而不是在旧文件末尾继续追加。
7. 执行下方的结构和内容校验。
8. 写回后重新读取文件确认结果；没有实质变化时不产生无意义修改。

## 证据和优先级

- 用户明确表达的偏好、意图、范围和决定，以用户当前表述为准。
- 当前本地探查决定文件、目录、版本、进程、配置和运行结果等可观测事实。
- 当前项目文件和 Git 状态优先于旧上下文中的描述。
- 官方文档或可靠外部资料用于确认外部规则、版本和时间敏感信息。
- 旧 `CONTEXT.md` 只能作为待核对线索，不能单独证明事实仍然成立。

用户的陈述与本地客观状态冲突时，不静默替用户裁决。保留冲突并标记“待确认”，只在该冲突会影响后续操作时询问一个明确问题。

## 条目状态

需要区分以下状态：

| 状态 | 含义 | 在当前上下文中的处理 |
|---|---|---|
| 已确认 | 有当前证据支持 | 保留 |
| 进行中 | 尚未完成且仍属于当前目标 | 保留在当前状态或下一步 |
| 待确认 | 证据不足或存在冲突 | 明确写出缺少的确认，不当作事实 |
| 已解决 | 已完成或问题已排除 | 从活动区块删除；可复用的经验压缩到踩坑记录 |
| 已替代 | 已被新路径、版本、决定或方案取代 | 删除旧表述，保留新的当前表述 |
| 历史 | 只用于解释过去，不影响当前工作 | 通常从 `CONTEXT.md` 删除，由 Git 历史保存 |

## 全量清理规则

- 每次同步都检查所有旧条目，不因文件尚未超过长度上限而跳过清理。
- 已完成的下一步直接删除，不在“下一步”中保留“已完成”复选框。
- 用户明确说已完成、放弃或暂不处理的事项，从活动任务中删除。
- 已不存在的路径、版本或工具不再作为当前环境描述。
- 已解决的问题从“活跃问题”删除；只有仍可能复现的通用经验才进入“可复用踩坑”。
- 重复、过细、可从代码或 Git 直接推导的内容删除。
- 旧路径、旧版本或旧方案只有在能防止再次误判时，才保留一行并标注“历史”。
- 不确定的内容标记“待确认”，不使用猜测填空。

## 当前上下文结构

只保留有内容且对后续工作有用的区块。推荐顺序如下：

```markdown
# [项目名称] — 上下文

## 项目目标

## 当前状态

## 下一步

## 用户约束

## 关键决策

## 可复用踩坑

## 活跃问题

## 文件入口

---
_最后核对：YYYY-MM-DD_
```

不为外包、学术或其他项目类型预先生成无关区块。环境信息只记录非标准、易变化且后续确实需要的配置。

## 各区块的内容边界

- `项目目标`：一句话说明项目要达到什么结果。
- `当前状态`：说明已完成的主线、正在处理的事项和主要阻塞。
- `下一步`：只写当前仍要执行的事项，按优先级排列，最多 3 条。
- `用户约束`：只写用户明确要求长期遵守的工作方式或范围限制。
- `关键决策`：只写会影响后续方案的决定及简短理由。
- `可复用踩坑`：只写可能再次遇到的问题和有效处理方式。
- `活跃问题`：只写尚未解决且会影响后续工作的事项。
- `文件入口`：只列下一次工作需要直接打开的文件或目录。

“近期工作”不是必需区块。若保留，只保留最近 3 条，并在完整同步时整体重建，不把它当作无限增长的日志。

## 长度和质量校验

同步完成前必须确认：

- 目标长度为 150～250 行，超过 300 行时立即压缩，不能超过 300 行。
- “下一步”最多 3 条，且每条都可执行、可判断完成。
- 没有重复事实、重复标题或互相矛盾的当前表述。
- 没有把已解决事项、已完成复选框或旧路径继续写成当前任务。
- 当前环境事实注明核对日期，易变化的事实不会无期限沿用。
- 文件重新读取成功，内容结构完整。
- 连续执行两次同步时，第二次没有实质变化。

## 写入和失败处理

- 先生成并校验完整新内容，再替换原文件。
- 写入失败、读取失败或校验失败时保留原文件，并说明失败原因。
- 不能确认的内容转为“待确认”，不能用推测覆盖旧事实。
- 不删除具有独立价值的历史信息；需要时交给 Git 历史或用户另行保存。
- 不记录密码、令牌、私钥或完整的敏感命令输出。

## hooks 的职责边界

收到 hook 提醒后，AI 才执行本 skill 的完整同步协议。hook 的输出是触发信号，不是同步收据。

- `SessionStart`：提醒读取完整上下文并确认当前状态。
- `UserPromptSubmit`：提醒检查本轮用户是否修正了事实、范围或偏好。
- `PostToolUse`：提醒在发生实际变化后执行同步，不要求每次工具调用都改文件。
- 会话结束或用户明确要求时：执行完整同步并按需报告变更。

AI 不得因为 hook 只提醒了一句话，就把完整同步缩减为“追加一行近期工作”。

## 常见错误

- 只写本轮做了什么，没有重新检查旧内容。
- 看到新事实后追加一条，却不替换相互冲突的旧事实。
- 把“没有再次看到”误判为“已经不存在”。
- 把用户说“完成”理解为在待办后面加完成标记，而不是删除待办。
- 把无法验证的旧内容继续写成当前事实。
- 为了保留历史而不断扩大当前上下文。
- 没有重新读取文件，就声称同步完成。

## 显式指令

| 用户指令 | 行为 |
|---|---|
| 更新上下文 / `update context` | 立即执行完整同步，并简要说明新增、修改、删除和待确认内容 |
| 读取上下文 / `load context` | 只读取并汇报当前状态，不修改文件 |
| 显示上下文 / `show context` | 输出当前 `CONTEXT.md` 全文，不修改文件 |
| 初始化上下文 / `init context` | 文件不存在时按最少必要信息初始化；已有文件时先询问是否覆盖 |
| 重置上下文 / `reset context` | 说明清空风险，得到确认后才能重建 |

## 完成标准

只有同时满足以下条件，才能说上下文同步完成：

1. 全文已读取，所有旧条目都被重新判定。
2. 当前事实、活跃任务、用户约束和关键决策均已反映。
3. 已解决、已替代和明确放弃的内容不再出现在活动区块。
4. 未确认内容已明确标记，未进行猜测性补全。
5. 长度、结构、重复项和写回结果均已验证。
